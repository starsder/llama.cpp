commit 4aaef90b93859c914d894384a48665a708ef24ee
qwen4exp: AVX2 i-quant experiments - gather is slower on Zen 3, ceiling is the codebook
Both experiments run and measured, both reverted:
 - in-register index assembly + _mm256_i32gather_epi64: correct (test-backend-ops 11/11 OK)
   but 1.8x SLOWER (1.29 vs 2.30 GB/s) - Zen 3's gather is microcoded;
 - _mm_loadl_epi64 + punpcklqdq + vinserti128 instead of _mm256_set_epi64x: 0% (2.30 vs 2.30),
   the compiler already emits the optimal sequence.

Structural reason, verified from the tables: the i-quant grids are learned codebooks.  Their
output bytes take only 3 values {8,25,43}, but the index->byte map is not a positional function
(no 1/2/3-bit field explains any output byte), so it cannot be computed with shifts + vpshufb -
a table lookup is required.  AVX2 has no byte gather and its 32-bit gather is slower than scalar
on this CPU.  The q2_K comparison (48.6 G weights/s at 2.625 bpw vs 7.2 for iq2_s at 2.56) is
therefore a property of codebook vs plain bit-packing, not of missing optimisation.

Correction to 6.35: the repack buffer IS registered and considered (llama-model.cpp:1073-1078
calls ggml_backend_dev_get_extra_bufts; the string 'repack' never appears because the mechanism
is generic).  What is true is that the loader allocates nothing in it - no CPU_REPACK buffer line
appears - because our host tensors land in CUDA_Host (experts, for the cache) and CPU_Mapped.
