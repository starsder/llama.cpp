# 00 研发主线：从 PLE 节省主存，到预测、传输与正确性

**项目的起点是 PLE，不是后来的 host 性能账本。** 最初的问题是：怎样避免把庞大的 PLE 表全部留在主存，同时仍能快速取到要用的行？后来的专家缓存沿用了“只保留真正要用的小部分数据”的思路，但增加了预测时机、异步传输、GPU 驻留与 CPU/GPU 分工等难题。

研发顺序与转向动机按[维护者回述](sources/author-recollection.md)补齐；具体机制、数字、失败与修复由各专题和[原始证据索引](evidence/README.md)支撑。部分工作并行推进，以下是因果主线，不是假装每次改动都有精确可核实的时间戳。

## 一、PLE：先解决 SSD → 主存，而不是先追 GPU token/s

### 原始问题

目标 GGUF 的 `per_layer_token_embd.weight` 约 26.8 GiB。若只为用到其中少量行而让整张表长期占用主存，就挤占了专家权重、系统与其他工作集的空间。

第一步因此是 **SSD 映射加载路径上的主机 PLE 行缓存**：保留磁盘上的量化表示，缓存所需页面／行并利用预取；不是改模型数学，也不是重新量化 PLE。

### 得到了什么

维护者报告的早期实测是：**约 1G 的 PLE 缓存占用，达到 90% 以上命中率**，可以释放大量原本需要 PLE 常驻的主存。这是这条路线最初的成功标准，不能事后只用 full-RAM 下的 token/s 去否定它。

现存相关日志还包含主机 PLE、GPU L1、预取开关、不同容量和不同长度的实验。它们不是同一组数字：例如主机层 `ablation-ple-only.csv` 的累计命中约 93.1%，GPU L1 的 `ple-gpu-overlap-stats.csv` 约 93.4%。后者**不能**冒充 SSD→主存的命中证据；对应协议、缓存层级、容量与预取行为见[01 章 PLE 小节](01-host-and-devpart.md)。

### 为什么后来不作为主配置

接着用类似思路做 GPU PLE 缓存，但加速有限。再后来，目标工作点变成权重完整驻留主存，早先要缓解的 SSD 读取问题已经改变，GPU PLE 又与 MoE 专家缓存、KV 和 workspace 竞争显存。

于是，full-RAM／MoE 优先配置关闭 PLE。**这是收益前提与资源分配的变化，不是 PLE 行缓存方案失败。** 以后若重新面向 SSD／低主存部署，早期的 PLE 结果仍值得复用。

## 二、专家缓存第一版：静态热表 + XT

PLE 证明“缓存真正访问的数据”有价值，下一步转向 MoE 专家权重。

最先采用的是容易实现和解释的组合：

- **静态热表**：从轨迹里统计每层高频专家，提供驻留底座。
- **XT**：从当前 token 的专家选择预测下一个 token 同层的专家，有约一整圈层遍历的提前量。
- **CrossLayer 对照**：相邻层转移表，便于离线估计覆盖率，再与静态表并集比较。

这阶段留下了 manifest 格式、hold-out 回放、静态／转移表消融和 lazy 模式容量扫描。收益并非零成本：pin 会消耗显存和槽位，也会固定住未必适合新分布的热集。

**为什么继续找预测器。** 静态表不够灵活，XT 的覆盖也不够好；缓存可以命中，但离“按需把正确专家及时送到 GPU”还有距离。它们后来保留为种子或显式对照，不再充当主预测器。[详见 PC-01–PC-04](02-prediction-and-cache.md)。

## 三、Fate：从隐藏状态提前预测，第一次受挫

下一步尝试 Fate 式思路：提前使用当前隐藏／gate 输入和下一层 gate 权重，预测后续专家，避免等待真实路由完成才开始传输。

维护者明确回述：**当时的尝试没能从隐藏层里榨取出足够有用的信息，因而受挫。** 档案保留这个转向原因，而不是把历史写成一路顺利地换了几个预测器。

同时限定结论：这是本项目当时的本地方案，不是 Fate 论文被证明无效，也不代表所有隐藏状态预测都不可能。现存运行日志未找到完全对应的启用记录，不能补造当时的精确命中率。[详见 PC-05](02-prediction-and-cache.md)。

## 四、共享专家 SMoE：teacher 99% 让在线实现值得一试

受挫后，转向 **SMoE 式利用共享专家**：共享专家总会计算；再结合当前输入和已经可用的部分 routed 贡献，构造后续 gate 的代理输入，不必等所有冷专家完成。

**关键转折是 teacher 测试命中率 99%。** 这是维护者直接报告的实测结果，也是开始在线实现的动机。档案不拿后来另一组 `recall@10` 去替换或否定它；完全对应的候选集、分母与测试协议尚待原始记录对应。

后续还做了可追溯的 N+k teacher-forced 对照，研究提前量增加时的退化，并发现某个数据集上 input-only 与完整代理的差距很小。这提出了进一步删依赖的可能，但**离线近似相近不等于已把在线路径改成 input-only**，更不等于累计生成质量已验证。

**这一步证明了“值得实现”，没有证明“在线一定快”。** [详见 PC-06–PC-11](02-prediction-and-cache.md)。

## 五、真正的工程难题：预测准，仍然可能交付得晚、传得多

在线链路比 teacher 测试多出一整套条件：

```text
候选专家预测
    ↓
准入与去重
    ↓
权重拷贝提交／排队
    ↓
消费前完成并保持驻留
    ↓
正确路由和 slot 绑定
    ↓
CPU/GPU 两边完整计算
```

这里陆续遇到：逐层读回和 event 等待、异步 worker、pinned staging、非阻塞结果晚一拍、rank 截止线、在途去重、静态热表污染预测覆盖口径、错误的 gate-softmax 淘汰分数，以及热区回填和冷启动。

最反直觉的一组历史记录是：预取约 **161→464 MB/token**，命中 **40.2%→58.2%**，速度却 **14.3→10.6 t/s**。这不是当前发布构建的受控基准，但它把目标从“命中越高越好”改成了“命中带来的收益能否覆盖传输和等待”。计时斜率倒数约 13.8 GB/s，不是实测 PCIe 峰值。

另一个例子：同步 `AHEAD=1` 可显著改善预测排名命中，但新增同步代价又会抵消收益。**准确率与可用提前量要一起看。** [机制与更正见 01、02、05 章](02-prediction-and-cache.md)。

## 六、双门控：从“尽量命中”改成“有净收益且赶得上”

这条算法路线是上述矛盾的收敛点，不应淹没在环境变量清单里。

### 第一门：值不值得传

源码 `moe_cache_effective_rank_cut()` 按预测排名估计每字节命中收益，和门槛比较，决定取到哪一名。

- 可以保留固定 cutoff，避免隐式依赖 `n_used`。
- 可以用 YIELD_AUTO 对 token 时间做小幅探测，调 `yield_min`。
- 可以用 TREND_AUTO 拟合 `time ≈ a − V × hits + P × MB`，把 `P/V` 作为盈亏平衡门槛，并配合迟滞、约束与拟合拒绝。
- 字节预算限制传输速率，与“单次候选值不值”不是一个问题。

### 第二门：来不来得及

`moe_prefetch_feasible()` 估计在飞工作加本批拷贝的到达时间，与距离消费还有多少层、每层耗时 EWMA 给出的 deadline 比较。预测传输赶不上时，不必继续堆队列，专家仍有 CPU 计算路径。

其中 `70 µs/copy`、`20 GB/s` 是模型常数，不是从本机实测学出的带宽；自适应部分包括层耗时和在飞量。调用范围及 bypass 条件也必须按源码看，不能宣称所有缓存写入都受这两个门控制。

### 为什么不是所有自适应都默认开

极值搜索有探测成本，回归会受预热、共线性和状态变化影响；早期几个阈值／预算方案也输给过固定 cut。算法本身保留了对问题的正确分解，不意味着每个控制器都已优于固定配置。

**与后来的频率门分开。** 全来源 frequency gate 是另一项“候选是否比 victim 更热”的准入实验，并不是双门控本身；它后来减少字节却没有稳定提速，已被否掉。[判据、公式、默认与失败表见 PC-12–PC-24](02-prediction-and-cache.md)。

## 七、dev 路径：为了减少 host 干预，却先碰到时序正确性

host 路径要回读路由、分区、发布 leaf，再启动两边计算。devpart 尝试把更多分区／驻留判断放在 GPU，减少主机参与。

随后出现的不是一个 bug，而是一串接口契约问题：host leaf 与 GPU 路由谁先写谁先读、WGT staging 是否真的提交、设备驻留表是否发布、按名字找激活是否找错、slot view 与原专家 ID 是否一致、CPU 半边是否真正计算。

因此有一段必须完整保留的更正链：**慢的初版 → 看起来飞快但少算／错算 → 逐项修正 → 正确路径不再快 → 不作为默认。** 不能只留最高的 28–32 t/s。

同时，host split 又发现独立的旧路由拷贝问题，导致此前“封板”的 20.3 t/s 也要撤回。最终 master 选择的是包含该路由复制修复与 UD 几何防护的保守 host 基线，不是最早看起来快的提交。[完整迭代见 01 章，正确性判据见 05 章](01-host-and-devpart.md)。

## 八、权重量化与 CPU 内核：没有忽略，但不能脱离瓶颈谈 SIMD

接着回头审视量化与内核：既然 CPU 半边存在，IQ 的解码与 dot 会不会才是慢点？

先纠正一个前提：`UD-IQ3_XXS` 是混合配方标签，实际最大字节来自 IQ4_NL，专家 gate/up 大多是 IQ2_S，另有 IQ3_S。按文件名推断内核，方向一开始就会错。

单核数据确实显示某些 grid-codebook IQ 内核在 Zen 3 上远慢于相近位宽的 K-quant：码本读取、索引组装和解包方式不同。尝试过 gather 与去插入；一个更慢，一个基本不变。IQ4_XS 8×8 重排后来有 microbench 收益，但既定模型／buffer／算子路径并没有因此自动变快。

**结论不是“IQ 都慢”或“AVX2 没救”。** 要看具体 dtype、backend、算子、buffer 选型，以及这部分成本是否真的位于关键路径。[量化选型与全部反例见 03 章](03-weight-quantization-and-kernels.md)。

## 九、TQ4/TBQ4：省了 KV，却在质量和执行路径上栽了

更长上下文和视觉把显存预算挤紧后，KV 压缩可以给 MoE 缓存腾槽。于是比较 f16、q8_0、q4_0、TBQ3、TBQ4。

- 用户所说 TQ3/TQ4 在这组代码中是 `tbq3_0` / `tbq4_0`，不是上游三值权重量化 TQ1/TQ2。
- TBQ4 短输出看起来正常，却出现 PPL 约 65、长一点的评测无结果退出等反证。
- TBQ3 的 CUDA FlashAttention 白名单／实例覆盖有缺口；TBQ4 则已进入另一条 FA 路径。两者不能因为位宽相近就假定走同一套实现。
- 关闭旋转仍坏；直接关闭 FA 又被量化 V cache 的要求拒绝。排除了部分猜想，不等于精确根因已经修复。

**256k 在这里主要是容量配置，质量数字来自短语料协议。** TBQ3 当时是容量优先候选，q4/q8 是不同保真折中；TBQ4 不能因省槽就作为可用配置。[完整矩阵和失败探针见 04 章](04-kv-tbq-and-nxq.md)。

## 十、NXQ：先把端点做对，再发现参考协议与记账并不等价

NXQ/E8 探索继续追低比特 KV，但再次暴露两层问题。

**工程端点。** 陪集信息、256 元素块与 32 元素索引的混淆、scale 下溢、CPY/SET_ROWS、坐标投影后再选择、整 head 的旋转——每一步都有单独的修复与证据。GPU 存 packed KV、读时物化为 f16 再调用现成 FA，也不等于实现了原生 packed FlashAttention。

**实验解释。** NexusQuant 0.6.3 的参考运行时保存 fp16 fake-quant 结果，int8＋时间差分＋zstd 是离线压缩记账；本地定长 NXQ 的真实占用不能与参考名义 bit 数直接互换。后来的本地图上 fake-quant 控制试验仍使用本地受限编码器，不能自称完全复现原版。

补 K 去 RoPE 没显示更低的均值 KLD；边界保护在已测点有均值改善，但层数原来算错：**48 个 block 中只有 12 个 full-attention KV 层**。原表的 48/44/40 应按实际量化对象解释成 12/11/10；由错误分母导出的“保护约 80% 层”没有依据。数据保留，外推撤回，也不能反过来预设进一步保护一定无效。

**这条路线仍属于未提交研究，不是 master 已交付的功能。** [见 04 章](04-kv-tbq-and-nxq.md)。

## 十一、后续共享池与驻留期：问题进一步落到“谁被搬了、是否真用过”

共享池与 LFU_POS 尝试把槽位从冷层调给未来要访问的热层。压力实验提高了命中，但 DMA 计数几乎不降，速度改善没有稳定超出运行波动。

于是补驻留期账本，区分预测／非预测准入、去重、未用淘汰、使用一次／多次、短间隔重装。再据此尝试全来源频率门与仅 hot 回填修复：前者被否，后者解决了一些逻辑 fixture 问题，但固定历史仍有 logits 差异，完整 CLI 又出现低于门槛与退出崩溃。

这些未通过验收的尝试没有被包装成成果，也没有因暂停而从档案中消失。[见 PC-28–PC-36](02-prediction-and-cache.md)及[方法学与事故](05-correctness-and-methodology.md)。

## 最后保留下来的，不是一句“快了多少”

- PLE 的价值首先是避免 SSD 场景下的大量主存常驻；full-RAM 的取舍不能抹掉这个起点。
- teacher 高命中是走向工程实现的有力动机，但在线收益必须穿过准入、传输、deadline、驻留和正确计算。
- 双门控把“值得传”和“来得及”分开；生命周期账本又把“曾经搬进来”和“真的用过”分开。
- 时序错误、量化路径不完整、统计分母错误都会制造漂亮数字。撤回和纠正本身就是研究成果。
- 只有带着具体协议、失败记录和版本边界，下一位维护者才能决定某条路线是该重试，还是不必再踩一次。
