# 维护者补充的研发顺序

来源：维护者在整理实验档案时直接补充的项目回述。它用于补足后期账本没有覆盖的研发起点与转向动机；不是新跑测，也不为缺少协议的指标自动补造分母、样本数或日期。

## 时间顺序与转向原因

1. 第一个做的是 **PLE 缓存**。
2. 然后开始专家缓存／SMoE 缓存方向，最初采用 **静态表 + XT**。
3. 接着尝试 **Fate**，希望从隐藏状态提取预测信息，但在本项目当时的尝试中未得到足够有用的信息，因而受挫。
4. 随后转向 **SMoE 式利用共享专家的方式**。维护者明确报告：**teacher 测试命中率达到 99%**。
5. 在离线结果鼓舞下开始在线实现，随后遇到一系列工程问题，包括 **命中率提高却更慢**。
6. 最后形成 **双门控的自适应传输阈值算法**，不能把这段研究简化成只追求最高命中率。
7. 后续发生 **dev 路径时序错误、TQ4 崩溃、NXQ 探索以及各类修复**，应与原始日志和代码记录结合整理。

## 证据边界

- 研发顺序与当时的动机按维护者回述记录，不以较晚的 handoff 章节顺序取代。
- `99%` 是维护者报告的 teacher 测试结果；若尚未找到完全对应的原始协议，就明确保留这一缺口，不改写该结果，也不把其他 recall@k、联合候选覆盖率或在线缓存命中率当作它的分母。
- Fate 在当时本地方案中未满足需求，不等于对 Fate 论文或所有隐藏状态预测方法的普遍否定。
- “TQ4”对应到实际实现的命名和故障路径，见[KV 量化复盘](../04-kv-tbq-and-nxq.md)；不能和同名近似格式混为一谈。

## PLE 起点与后续取舍的补充

维护者进一步说明：

- PLE 首先解决的是 **SSD → 主存** 的数据读取问题，不是先做 GPU 加速。
- 在映射加载路径（维护者原文称 `nmap`，代码／文档通常称 `mmap`）下，实测 **约 1G PLE 缓存占用，命中率 90% 以上**，可避免大量 PLE 数据完整常驻主存。
- 后来按类似思路加入 GPU PLE 缓存，但加速不高；在权重完整驻留主存的工作点下，帮助也不大。
- 因此，在 full-RAM／MoE 预算优先配置中关闭 PLE，不代表其在 SSD 映射加载场景下无效，也不代表否定最初的内存节省目标。

`1G` 与 `90%+` 按维护者报告保留；没有完全对应的原始日志时，不擅自把单位精确化为某个 MiB 数、填入样本量，或换算成 token/s 提升。早期 mmap 成功实验与后续大权重页锁定组合的 OOM 风险属于不同设置，不能将任一方推广成所有 mmap 用法的结论。
